FoodLink Business App — Backend-Schema Drift Audit
====================================================

Reference point: services/identity-service HEAD — business_locations->store
rename (d4e5f6a7b8c9), StoreSetting 1:1 table, Business growth
(logo/registration_number/status/email/phone/address), one-business-per-user
+ device-lock.

Date: 2026-08-06
Status: Findings only — no files modified.


1. Naming drift (business_locations -> store)
---------------------------------------------

No occurrences anywhere.  Grepped business_locations, BusinessLocation,
business_location across lib/, test/, *.md, config — zero hits.  The app never
names the concept "Location"; all business scoping is via businessId
(correct).  There are also NO Store/StoreSetting Dart models yet — the app
simply hasn't consumed the store API.  Nothing to fix in this category.


2. Stale multi-business plumbing
--------------------------------

2.1  CachedBusinessContexts Drift table — DEAD CODE, over-built.
     File:  lib/core/storage/tables/cached_business_contexts.dart:4-21
     Registered:  lib/core/storage/app_database.dart:23
     Stores a LIST of roleNames/permissions plus contact/currency per
     business (StringListConverter at
     lib/core/storage/converters/string_list_converter.dart:4) — a shape
     designed for "roles at many businesses."
     No lib/ code ever reads or writes it; only consumer is a round-trip
     test at test/storage/app_database_test.dart:98-121.
     Under one-business-per-device it is superseded by DeviceConfig (device
     lock) + server-side onboarding-status.
     Severity: stale-but-harmless / worth removing (with converter + test).

2.2  LocalUserProfiles.activeBusinessId — never populated.
     Column:  lib/core/storage/tables/local_user_profiles.dart:9
     Plumbed through upsertProfile at
       lib/features/auth/data/local_profile_repository.dart:22,86,96
     but the only production caller, AuthNotifier.setPin()
     (lib/features/auth/application/auth_notifier.dart:205-210), never
     passes it, so it is always NULL.
     Leftover from a per-profile "active business" era, now redundant with
     the device-level lock.
     Severity: stale-but-harmless; removal needs schemaVersion bump +
     migration.

2.3  Business switcher — CONFIRMED ABSENT (nothing to remove).
     account_settings_screen.dart handles only profiles / End Shift /
     Remove Profile (correct — profile switching stays).  AuthState has no
     business-list variant; app_router.dart has no switcher route; no UI
     references switching between businesses.  The app's JWT parser reads
     only "sub" (lib/features/auth/data/identity_api.dart:175-189) and never
     the other_businesses / active_business_id claims.  Clean.


3. API contract drift
---------------------

3.1  BusinessCreateResult (lib/features/business/domain/business_create_response.dart:17-27)
     parses business.id, business.name, owner_role_name — all present in
     backend BusinessCreateResponse (schemas/business.py:91-101).
     No runtime break.  But there is NO Dart Business model at all; the new
     fields (logo, registration_number, status, email, phone, address,
     country_code, city, timezone, timestamps) are unmodeled.  Not needed by
     today's screens; add a model when a settings/dashboard screen needs it.
     Severity: fine today, gap for later.

3.2  BusinessCreateRequest (business_create_request.dart:35-43) field set
     matches backend BusinessCreateRequest exactly; new optional fields not
     sent, which is legal.  OK.

3.3  OTP/refresh token parse (identity_api.dart:163-173) reads
     access_token / refresh_token, matching TokenResponse
     (schemas/auth.py:111-117).  OK.

3.4  Onboarding-status parse (identity_api.dart:102-133) matches
     me.py:44-51 exactly, including SINGLE optional business_id — correct
     for one-business-per-user.  OK.


4. Onboarding flow
------------------

4.1  business_type selector removal — CONFIRMED CORRECT.
     BusinessType enum holds only restaurant (business_type.dart:6-18);
     the screen hardcodes it (business_onboarding_screen.dart:97,372);
     apiValue "restaurant" matches the backend enum; test asserts it at
     business_onboarding_screen_test.dart:126-158.

4.2  POST payload matches backend
     (business_onboarding_screen.dart:95-101 ->
     business_create_request.dart:35-43): name, business_type, optional
     tax_id/organization_id, country_code, city, timezone — all valid
     BusinessCreateRequest fields.  Response parse matches too (incl.
     owner_role_name).  OK.

4.3  LATENT TOKEN-SCOPING GAP (the one that matters).
     Backend BusinessCreateResponse.note (schemas/business.py:97-100)
     explicitly warns the caller's token does NOT reflect the new business
     and instructs POST /auth/context/switch.  The app ignores this: after
     createBusiness, completeOnboarding() (auth_notifier.dart:252-272) reads
     the DB-backed onboarding-status to set the device lock and flips to
     sessionActive — but the token in TokenStore stays the unscoped OTP
     token (active_business_id=None, roles=[], permissions=[]; see
     auth.py:108-115).  So the FIRST business-scoped call
     (stores/inventory/POS, GET /businesses/{id}) will 403 with "Switch to a
     business context first."  Works today only because the app calls just
     auth + onboarding-status endpoints.
     Severity: LATENT — breaks at the first business-data integration.
     Decide: app calls context/switch post-onboarding, or backend
     auto-scopes.

4.4  Dead strings / doc drift (3-step leftover).
     app_strings.dart:58-61 (onboardingBusinessTypeStepTitle/Subtitle),
     :79-80 (onboardingBusinessTypeRequired) are unreferenced remains of the
     removed type-selector step; also dead: :53-54 onboardingSubtitle, :55
     onboardingStepOf, :82 onboardingCreating, :85-87 onboardingNotStarted*.
     onboardingBusinessTypeLabel (:78) is still used (screen line 371).
     lib/features/business/README.md:7,17 describes a "three-step form" —
     the form is two steps.
     Severity: cosmetic.


5. Device-lock & profile-picker flow
------------------------------------

5.1  _resolveBootSession (auth_notifier.dart:97-119): compares the SINGLE
     optional businessId from onboarding-status against
     DeviceConfig.lockedBusinessId — correct single-id semantics; mismatch
     -> locked session.  OK.

5.2  setPin (auth_notifier.dart:184-197): rejects a new profile whose
     business differs from the device lock; sets the lock only for
     non-onboarding (invited-staff) users.  OK.
     NOTE: when the device is already locked, a needs_onboarding=true user
     (businessId null) is rejected by null != lockedBusinessId at :191 — a
     self-registering owner can never onboard on a device already locked to
     another business.  Probably intended, but confirm.

5.3  completeOnboarding sets the lock for owners post-creation;
     removeFromDevice clears it only when the last profile goes
     (auth_notifier.dart:510-524).  OK.

5.4  Edge: _resolveBootSession falls back to sessionActive(locked:true) on
     any network/token failure (:117-118), skipping the lock-consistency
     check offline.  Minor, defensive.

5.5  No list-based business assumption anywhere.  OK.


6. Other
--------

6.1  ApiClient._attemptTokenRefresh() is a stub returning false
     (api_client.dart:53-62), so TokenRefreshInterceptor (:91-115) never
     refreshes on 401; the explicit refresh in _resolveBootSession is the
     only path.  Pre-existing, not schema-related, but interacts with the
     rotating-refresh design — worth finishing before any dashboard data
     load.

6.2  BusinessType is now a single-value enum + selfRegistrable wrapper;
     business_create_request.dart organizationId is never set by the draft.
     Both harmless; simplify if touching the file.

6.3  .env / ApiEndpoints base-URL mismatch (10.0.2.2 vs localhost) —
     config only, out of scope.
